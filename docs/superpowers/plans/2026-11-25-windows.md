# MasterKeys for Windows 11 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remaps, macros, profiles and auto-switch on Windows 11 as one tray app, built and released by GitHub Actions to a public repo, with in-app one-click updates.

**Architecture:** On Windows the GUI starts the daemon library in-process and talks to it over the existing zbus interface, through a peer-to-peer connection on a loopback TCP pair. The OS-specific parts sit behind `cfg` seams with the same signatures as the Linux code: key input (hook / SendInput), process list, tray, single instance, autostart and log. The shared input pump, engine, profiles and GUI logic are reused unchanged.

**Tech Stack:**
- Already in use: Rust 2024, zbus 6 (p2p over tokio TCP), Slint 1.18.
- New for Windows: `windows-sys` (hooks, SendInput, Toolhelp, mutex/event, registry) and `tray-icon`.
- New for updates: `ureq` (rustls), `sha2`, `zip`, `self-replace`.
- GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-25-windows-design.md`

## Global Constraints

- The Linux build and its behaviour stay unchanged. Every task ends with `cargo clippy --workspace --all-targets` + `cargo test --workspace` green in `rexbuild`, and Windows CI green from Task 2 on.
- Key names, profiles and macro text are identical on both systems. Windows key codes translate to the evdev numbers `InputKey` already uses.
- Repo: `github.com/I-MnM-I/MasterKeys`, public. Commits use the GitHub noreply address already set in this repo's `git config user.email`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Config and log: `%APPDATA%\MasterKeys`. The log is `masterkeys.log`, rotated at 1 MB.
- Run key: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `MasterKeys`, data `"<exe>" --tray`.
- Updates: `https://api.github.com/repos/I-MnM-I/MasterKeys/releases/latest`, checked at startup and every 24 h. Assets are `MasterKeys-windows.zip` + `SHA256SUMS`. The update is installed only after the hash matches.
- On Windows: no lighting panel, no GameSense, no Apex 3 output.
- Never send `00 09 00` to the keyboard.
- Work happens on branch `windows`, cut from `macro-modes`.
- Pushing, creating the repo and publishing a real Release are outward-facing. Creating the repo and pushing were approved with the design. **Publishing the first real Release (`v0.2.0`) waits for the user's yes.**

## Review Focus

1. **A key held while remapping starts or stops on Windows** (for example the Enter that switched profile). No key may be left stuck down or up. Covered by Task 5 `release_of_key_down_before_grab_passes`, and by `grab_decision` being reused.
2. **The app stalls while grabbing.** The keyboard must not go dead: once the heartbeat is older than 1 s, the hook passes keys through. Covered by Task 5 `stale_heartbeat_passes_through`.
3. **A Linux profile copied to Windows** must load with the same keys. Covered by Task 4 `every_layout_key_round_trips`.
4. **An update with a missing asset, bad hash, or while offline or rate-limited** must leave the installed exe untouched and say nothing on a failed check. Covered by Task 9 `bad_hash_is_rejected`, `release_without_zip_cannot_install` and `failed_check_shows_nothing`.
5. **An exe path with spaces** (`C:\Users\Jo Smith\Downloads\…`) in the Run key. Covered by Task 8 `run_command_quotes_the_path`.

### Task 5: Keyboard hook and SendInput

**Files:**
- Create: `crates/masterkeysd/src/hookrules.rs` (pure, every OS)
- Modify: `crates/masterkeysd/src/input/windows.rs` (real backend)

**Interfaces:**
- Produces:
  - `enum HookMode { Off, Read, Grab }`
  - `pub const MAX_HEARTBEAT_AGE: Duration = 1 s`
  - `enum Action { Pass, Report, Swallow }`. Report means pass to Windows and send to the pump as `grabbed: false`. Swallow means send as `grabbed: true` and return 1.
  - `struct HookState`. It tracks which keys are down and which went down natively. It has `fn on_key(&mut self, mode: HookMode, code: u16, down: bool, ours: bool, heartbeat_age: Duration) -> (Action, i32 /*evdev value 0/1/2*/)`.
- Rules:
  - Our own injected events (`dwExtraInfo == MASTERKEYS_TAG`) → `Pass`.
  - Off → `Pass`.
  - Read → `Report`.
  - Grab with a fresh heartbeat → `Swallow`, unless it's the release of a key that went down natively (that release is `Report`).
  - Grab with a stale heartbeat → `Report`.
  - A down event for a key that is already down gives value 2.
- Windows backend:
  - One hook thread for the life of the process: `SetWindowsHookExW(WH_KEYBOARD_LL)` + `GetMessageW` loop. Shared state lives in a `static OnceLock<Mutex<…>>`, and events go to the pump through a tokio unbounded sender.
  - `read_keys` sets Read and forwards transitions through `PressTracker` to `gui` until `stop`.
  - `grab_session` waits for held keys with `GetAsyncKeyState` over every mapped code via `grab_decision`, then sets Grab. It runs a 100 ms heartbeat task and calls `pump` with a `SendInputSink`. When the pump ends it sets Read or Off.
  - `SendInputSink` implements `KeySink` with `KEYEVENTF_SCANCODE` (+`EXTENDEDKEY`), or the VK for media keys, tagged with `MASTERKEYS_TAG`.

- [ ] **Step 1: Write the `hookrules` tests and watch them fail:**
  - `grab_swallows_physical_keys`
  - `our_own_injected_keys_pass`
  - `read_reports_and_passes`
  - `off_passes`
  - `stale_heartbeat_passes_through` (age 1.5 s → `Report`)
  - `held_key_reports_repeat` (down, down → values 1, 2)
  - `release_of_key_down_before_grab_passes` (down in Read, up in Grab → `Report`)
- [ ] **Step 2: Implement `hookrules`.** Expected: green on Linux.
