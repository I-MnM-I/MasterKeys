# Milestone 2: Daemon — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `masterkeysd`, a systemd user service that is the only process touching the Apex 3. It exposes lighting control on the D-Bus session bus, runs animated effects, and reconnects by itself after an unplug.

**Architecture:** Two new crates. `masterkeys-core` holds the shared lighting state type and the D-Bus names plus a client proxy, which the GUI will reuse in M3. `masterkeysd` holds a device supervisor (open/reconnect, hidden behind a `Lighting` trait so tests use a fake), a renderer (turns state + time into frames with upstream's `EffectEngine`), the zbus interface, and `main`. Lighting state is the effect plus brightness. Per-zone colours are `Effect::Custom { colors }` and one colour is `Effect::Static`, so there is no second copy of the colours to drift.

**Tech Stack:** Rust 1.99.1, tokio, `zbus` 6.x (tokio feature), `serde_json`, `tracing` + `tracing-subscriber`, `steelseries-gg` (`apex3`, `rgb`).

**Spec:** `docs/superpowers/specs/2026-11-08-masterkeys-design.md` (milestone 2; "masterkeysd", "Error handling")

## Global Constraints

- Bus name `org.masterkeys.Daemon`, object path `/org/masterkeys/Daemon`, interface `org.masterkeys.Daemon1`, on the **session** bus.
- Only `masterkeysd` opens the keyboard. Never send `00 09 00` (save_to_flash).
- Brightness goes to hardware (`set_brightness`), never by scaling colours.
- Animated frames are sent at most every 16 ms (≈60 fps), whatever `EffectEngine::calculate_frame_budget` asks for. Static, Custom and Off states are sent once per change (and on reconnect), not in a loop.
- The `Reactive` effect needs key input (M5). In M2, `SetEffect` with `Reactive` is rejected with a D-Bus error saying it arrives with remapping.
- Over D-Bus, colours are `"RRGGBB"` strings and the state/effect are JSON strings (serde of the core types), so `busctl` can drive and read everything.
- Logs go to stderr via `tracing-subscriber` (journald captures a user service's stderr). Level comes from `RUST_LOG`, default `info`.
- zbus 6 is newer than the API examples most people know. Check `#[interface]`, `#[proxy]`, signal emission and `connection::Builder` against docs.rs for the exact 6.x version before writing them.

## D-Bus interface (M2 subset of the spec)

| Member | Signature | Behaviour |
|---|---|---|
| `GetState() -> s` | | JSON of `LightingState` + `"connected": bool` (see Task 1 `StateReport`) |
| `SetAllColor(s color)` | | effect := `Static { color }` |
| `SetZoneColor(y zone, s color)` | | effect := `Custom`; if the current effect isn't `Custom`, start from the colours currently shown, then set `zone`. Zone ≥ 10 → error |
| `SetBrightness(y percent)` | | 0–100, else error |
| `SetEffect(s effect_json)` | | parse `Effect`; reject `Reactive`; `Custom` must have exactly 10 colours |
| signal `StateChanged(s state_json)` | | after every accepted change (same JSON as `GetState`) |
| signal `DeviceConnected(b connected)` | | on every connect/disconnect transition |

Errors are D-Bus errors under `org.masterkeys.Daemon1.Error.*` (`InvalidArgument`, `Unsupported`) with a plain-English message.

## Review Focus

1. **Keyboard absent at daemon start** → daemon still starts and serves D-Bus, `GetState` reports `connected: false`, and it applies the state once the keyboard appears. (Task 3 test with a fake opener that fails first)
2. **Unplug while an animation runs** → the write error is logged once (not every frame), the device is dropped, reconnect retries with backoff (1 s doubling to a 10 s cap), and the animation resumes on replug. (Task 3 test)
3. **Second daemon instance** → exits non-zero with "masterkeysd is already running" because the bus name is taken. (Task 5 manual step)
4. **Bad input over D-Bus** (zone 12, `"zz0000"`, brightness 150, malformed JSON, 3-colour Custom) → D-Bus error, state unchanged, nothing sent. (Task 4 tests)
5. **Rapid changes during an animation** (e.g. a GUI slider sending 50 `SetBrightness` calls) → the latest state wins and nothing queues up unboundedly. (Task 3: state travels on a `tokio::sync::watch` channel, which keeps only the latest value; test it)

### Task 3: Device supervisor + output loop

**Files:**
- Create: `crates/masterkeysd/src/device.rs`, `crates/masterkeysd/src/output.rs`

**Interfaces:**
- Consumes: `steelseries_gg::apex3::Apex3Device` (`open`, `set_zones`, `set_brightness`), `Renderer`, `LightingState`.
- Produces:
  - `device.rs`: `pub trait Lighting: Send { fn set_zones(&mut self, c: &[Color; ZONE_COUNT]) -> steelseries_gg::Result<()>; fn set_brightness(&mut self, p: u8) -> steelseries_gg::Result<()>; }`, implemented for `Apex3Device`. `pub type Opener = Box<dyn FnMut() -> steelseries_gg::Result<Box<dyn Lighting>> + Send>;` and `pub fn apex3_opener() -> Opener`.
  - `output.rs`: `pub struct Shared { pub state: watch::Receiver<LightingState>, pub connected: watch::Sender<bool>, pub frame: Arc<Mutex<[Color; ZONE_COUNT]>> }` and `pub async fn run(opener: Opener, shared: Shared, backoff: Backoff)`, which never returns. `pub struct Backoff { pub initial: Duration, pub max: Duration }` with `Backoff::DEFAULT` = 1 s / 10 s.
  - Loop behaviour: while disconnected, try `opener()` and sleep backoff (doubling, capped) between failures. On connect, set `connected` true, send brightness + current frame. Then wait on whichever comes first: a state change (`state.changed()`), the renderer's `next_frame_in()` timer, or nothing if static. On state change, send brightness only if it changed, and always send the new frame. On any write error: log once at `warn`, drop the device, set `connected` false, reset backoff, go back to reconnecting. Write each frame into `frame` (for `SetZoneColor`).
