# Milestone 4: Profiles + Auto-switch — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Named lighting profiles saved on disk, switched by hand from the GUI or automatically when a linked game starts. Lighting survives a daemon restart.

**Architecture:**
- **Profile model and storage** (`masterkeys-core`): pure code, tested against a temp directory.
- **Process matching** (`masterkeys-core`): reads `/proc`.
- **Profile manager** (`masterkeysd`): an in-memory map, the active profile and the default profile, plus an auto-switch state machine. Both are plain structs with no I/O, so they're unit-tested.
- **Daemon wiring:** the service routes every lighting setter through the manager, so edits always land in the **active profile**. A saver task writes changes to disk within 1 s, and a watcher task polls `/proc` every 2 s.
- **GUI:** a Profiles panel.

**Tech Stack:** as M3, plus `tempfile` (dev).

**Spec:** `docs/superpowers/specs/2026-11-08-masterkeys-design.md` (milestone 4; `masterkeys-core` Profile/storage, `masterkeysd` process watcher, GUI Profiles panel)

## Global Constraints

- **Storage:** `~/.config/masterkeys/profiles/<name>.toml` (one per profile) and `~/.config/masterkeys/settings.toml` (`default_profile`, `active_profile`). Files are written atomically (write `*.tmp` with mode 0600, then rename).
- **Profile TOML:** `name`, `brightness`, `executables = [...]`, `[effect]` (serde of `Effect`). Remaps and macros arrive in M5, so they aren't in this format yet.
- **Legacy import:** a profile file in the old CLI-draft format (`name`, `brightness`, `[[zones]]` × 10 of `r/g/b`) loads as `Effect::Custom` and is rewritten in the new format on the next save. The user has one such file, `gaming.toml`.
- **Names:** 1–64 characters, no `/`, `\` or NUL, not starting with `.`, unique (case-sensitive). The file name is `<name>.toml`.
- **Lighting edits belong to the active profile.** Every `Set*` call updates the active profile and is saved (debounced, ≤ 1 s after the last change). There is no separate "Save" button.
- **First run:** if there are no valid profiles, create `Default` (white, 100 %) and make it the default.
- **Matching:** a link is a program name such as `eldenring.exe` or `factorio`, compared case-insensitively. A process matches if the basename of `/proc/<pid>/exe` equals the link, **or** the basename of any `cmdline` argument does (split on both `/` and `\`). The second rule catches Proton/Wine games, whose `exe` is the Wine loader. Only the user's own processes are read; any that can't be read are skipped.
- **Auto-switch rules:**
  - When a linked program starts, switch to its profile.
  - When it exits, switch to the profile of the most recently started linked program still running, or to the default if none is left.
  - A manual `ActivateProfile` holds until the next start or exit of a linked program.
  - If two profiles link the same program name, the one whose name sorts first wins.
- **Malformed profile file:** skipped and logged at `warn` with the file name. The daemon keeps running.
- **Deletes and renames:**
  - Deleting the last profile, or the default profile, is refused with an error that names the reason.
  - Deleting the active profile switches to the default.
  - Renaming moves the file and updates `settings.toml` if the profile was the default or active one.

## D-Bus additions (`org.masterkeys.Daemon1`)

| Member | Behaviour |
|---|---|
| `ListProfiles() -> s` | JSON `[{"name", "executables", "is_default"}]`, sorted by name |
| `ActivateProfile(s name)` | manual switch |
| `CreateProfile(s name)` | new profile copying the current lighting, with no links. Does not activate it |
| `DeleteProfile(s name)` · `RenameProfile(s old, s new)` | rules above |
| `SetProfileExecutables(s name, as executables)` | replaces the links. Trims entries, drops empty ones, dedupes case-insensitively |
| `SetDefaultProfile(s name)` | |
| signal `ProfilesChanged()` | after create / delete / rename / links / default changes |
| `GetState` / `StateChanged` | `StateReport` gains `"profile": "<active name>"` |

Errors are `InvalidArgument` for bad names or unknown profiles, and `Refused` for a delete or rename that breaks the rules.

## Review Focus

1. **Daemon restart** → comes back on the same active profile with the same lighting, and doesn't fall back to white. (Task 4 test with a temp config dir)
2. **Game exits while another linked game still runs** → switches to the other game's profile, not the default. (Task 3 test)
3. **User picks a profile while a game runs, then the game exits** → reverts to the default; while the game keeps running, the manual pick holds. (Task 3 test)
4. **Hand-edited profile file with a syntax error** → that file is skipped with a warning naming it, every other profile loads, and the bad file is **not** overwritten. (Task 1 test)
5. **Rename onto an existing name, or a name like `../x`** → refused, nothing on disk changes. (Task 1 and Task 4 tests)

### Task 3: Profile manager and auto-switch (daemon, pure)

**Files:**
- Create: `crates/masterkeysd/src/profiles.rs`

**Interfaces:**
- Consumes: `Profile`, `Settings`, `validate_name`, `ProcessInfo`, `matches`.
- Produces:
  - `pub struct Profiles` built by `pub fn from_loaded(profiles: Vec<Profile>, settings: Settings) -> Self`. That function applies the first-run `Default` rule, falls back to the first profile by name when the default is missing, and starts on `settings.active_profile` if that exists, else the default.
  - Methods:
    - `active(&self) -> &Profile`
    - `default_name(&self) -> &str`
    - `list(&self) -> Vec<&Profile>` (sorted)
    - `activate(&mut self, name) -> Result<(), ProfileError>`: manual switch
    - `set_lighting(&mut self, state: LightingState)`: edits the active profile
    - `create(&mut self, name) -> Result<(), ProfileError>`
    - `delete(&mut self, name) -> Result<(), ProfileError>`
    - `rename(&mut self, old, new) -> Result<(), ProfileError>`
    - `set_executables(&mut self, name, Vec<String>) -> Result<(), ProfileError>`
    - `set_default(&mut self, name) -> Result<(), ProfileError>`
    - `settings(&self) -> Settings`
  - `pub enum ProfileError { Invalid(String), Refused(String) }` (`Display`).
  - `pub struct AutoSwitch` with `pub fn update(&mut self, profiles: &Profiles, running: &[ProcessInfo]) -> Option<String>`. It returns the profile to switch to when the set of running linked programs changes, per the auto-switch rules. It tracks the linked processes seen (pid + start) between calls, and returns `None` when nothing relevant changed, so a manual pick holds.

### Task 4: Daemon wiring

**Files:**
- Modify: `crates/masterkeysd/src/service.rs`, `crates/masterkeysd/src/main.rs`, `crates/masterkeys-core/src/state.rs` (`StateReport.profile: String`), `crates/masterkeys-core/src/dbus.rs` (proxy additions)
- Create: `crates/masterkeysd/src/persist.rs` (saver + watcher tasks)
- Test: `crates/masterkeysd/tests/dbus.rs` additions

**Interfaces:**
- `DaemonService::new(state, connected, frame, keys, profiles: Arc<Mutex<Profiles>>, dirty: watch::Sender<u64>)`.
  - Each lighting setter validates, then calls `profiles.set_lighting(...)`, sends the state, bumps `dirty`, and emits `StateChanged`.
  - The profile methods are those in the D-Bus table. A successful activation also sends the new profile's lighting into the state watch.
  - Every profile-list change bumps `dirty` and emits `ProfilesChanged`.
- `persist.rs`:
  - `pub async fn saver(store: ProfileStore, profiles: Arc<Mutex<Profiles>>, mut dirty: watch::Receiver<u64>)` waits for a change, then 1 s of quiet. It then writes every changed profile and `settings.toml`, and deletes or renames files to mirror the manager.
  - The simplest correct approach: `Profiles` keeps a `pending: Vec<StoreOp>` journal (`Save(name)`, `Delete(name)`, `Rename(old, new)`, `Settings`) that `saver` drains.
  - `pub async fn watcher(service_handle, profiles, auto: AutoSwitch)` polls `process::running()` every 2 s. When `AutoSwitch::update` returns a name, it activates that profile through the same path as `ActivateProfile`, and logs `info: auto-switch to "<name>" (<program> started|exited)`.
- `main.rs` loads the `ProfileStore` from `default_config_dir()` (env override `MASTERKEYS_CONFIG_DIR` for tests and manual checks), logs each load warning, builds `Profiles`, seeds the state watch from the active profile, and spawns the saver and the watcher.
